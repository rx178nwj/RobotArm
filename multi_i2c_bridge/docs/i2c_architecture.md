# コントローラ ⇔ ブリッジ間 I2C制御アーキテクチャ設計

上流バス（Controller ⇔ RP2040ブリッジ）の通信アーキテクチャ検討

## 0. 前提と役割定義

| 主体 | I2Cロール | 説明 |
|------|-----------|------|
| Controller（上位） | **Master / Controller** | 通信を開始する側。SCLを駆動 |
| RP2040 ブリッジ | **Slave / Target**（アドレス 0x42想定） | 要求に受動応答。下流のセンサ集約結果を提供 |

**基本方針**：ブリッジは上位に対して「1個のI2Cセンサデバイス」として振る舞う。上位は下流の TCA9548A / AS5600 / ポーリング手順を一切意識せず、**レジスタの読み書きだけ**で6ch角度を取得する（下流の複雑さをブリッジ内に隠蔽）。

---

## 1. 通信モデルの選定

3案を比較し、**レジスタマップ型（ポインタベース）** を採用する。

| モデル | 概要 | 長所 | 短所 | 採否 |
|--------|------|------|------|------|
| **A. レジスタマップ型** | 汎用I2Cセンサ同様。ポインタを書いてから読む | 上位が汎用I2Cドライバ流用可、実装枯れている、部分読み可 | ポインタ状態管理が必要 | **採用** |
| B. コマンド/レスポンス型 | コマンドバイト＋パラメータで手続き駆動 | 複雑な操作を表現しやすい | 上位実装が独自化、オーバヘッド | 補助的に一部採用（CMDレジスタ） |
| C. 生ストリーム型 | 常に固定フォーマットを垂れ流し | 最小オーバヘッド | ランダムアクセス不可、拡張性低 | 不採用 |

> 採用理由：上位コントローラ側は Linux i2c-dev / MCUの標準I2Cドライバをそのまま使え、SMBus的な「レジスタ読み出し」慣習に一致するため実装・デバッグが容易。

## 2. トランザクション仕様

### 2.1 レジスタ書き込み（ポインタ設定 / 設定変更）

```
[S][ADDR+W][ptr][data0][data1]...[P]
        │     │     └─ ptr から auto-increment で書込（R/Wレジスタのみ）
        │     └─ レジスタポインタを更新
        └─ 0x42 + Write
```

### 2.2 レジスタ読み出し（コンバインド形式・推奨）

```
[S][ADDR+W][ptr][Sr][ADDR+R][d0][d1]...[dn][NACK][P]
        │    │    │     │     └─ ptr から auto-increment で連続読出
        │    │    │     └─ 0x42 + Read
        │    │    └─ Repeated START
        │    └─ 読み出し開始レジスタを指定
        └─ 0x42 + Write（ポインタ設定のみ、データ無し）
```

### 2.3 現在ポインタからの読み出し（ポインタ設定省略）

```
[S][ADDR+R][d0][d1]...[NACK][P]   ← 前回ポインタの続きから読める
```

### 2.4 6ch一括取得（代表ユースケース）

`CH0_ANGLE`(0x10) から **12バイト連続リード** で ch0-5 の角度を一度に取得（§2.2の形式、ptr=0x10, n=12）。これにより6ch分が**単一トランザクションの一貫スナップショット**で読める（§4参照）。

## 3. RP2040内部アーキテクチャ（タスク分割）

デュアルコアを活かし、**上流応答**と**下流ポーリング**を物理的に分離する。

```
        Core0 : 上流I2Cターゲット (受動・低レイテンシ応答)
        ┌──────────────────────────────────────────┐
        │  I2C0 Slave ISR                            │
        │   ├ アドレス一致 / RESTART 検出            │
        │   ├ RX: ポインタ・設定書込を受領            │
        │   ├ RD_REQ: TXステージングから1バイト供給   │
        │   └ STOP: トランザクション確定              │
        │           ▲ 読出時は publish済スナップショット│
        └───────────┼──────────────────────────────┘
                    │  ダブルバッファ (atomic index swap)
        ┌───────────┼──────────────────────────────┐
        │  ポーリングループ                          │
        │   loop:                                    │
        │     mux CH0選択→AS5600読出→shadowへ         │
        │     mux CH1..CH4選択→AS5600読出→shadowへ    │
        │     mux CH5選択→AS5600読出→shadowへ         │
        │     shadow を active に publish (index swap) │
        │  I2C1 Master                               │
        └──────────────────────────────────────────┘
        Core1 : 下流I2Cマスタ (能動・周期ポーリング)
```

- **Core1**：下流バスを占有し、mux切替＋AS5600読出しを周期実行。結果を shadow バッファに書き、1巡完了ごとに active バッファへ publish。
- **Core0**：上流スレーブISRのみを担当。読み出し要求には publish 済みバッファから即応答（下流通信の完了を待たない）。

> シングルコアでも実装可能だが、その場合は下流マスタ処理を非ブロッキング化（ステートマシン化）し、スレーブISRを最優先にする必要がある。デュアルコア分離の方が設計・タイミング保証が単純。

## 4. データ整合性（最重要）

### 4.1 課題

下流ポーリング（Core1）は上流読み出し（Core0）と非同期。6バイト一括リードの途中でバッファが更新されると、**ch0は新サンプル・ch2は旧サンプル**という tear（ちぎれ）が発生する。

### 4.2 対策：ダブルバッファ + トランザクション開始時ラッチ

```
active_idx (1ワード, アライン=アトミック更新)
   ├─ buf[0]  ┐
   └─ buf[1]  ┘  ← Core1が非activeへ書込→完了後 active_idx をswap

読み出しトランザクション開始（Sr+ADDR+R検出）時：
   1. active_idx を読み、対象bufを tx_staging[] に memcpy（マップ全体〜数十バイト）
   2. 以降のバーストは tx_staging から供給
   → トランザクション中にswapが起きても、読み手は一貫スナップショットを見る
```

- Core1 は「全ch書込完了 → publish」の順を厳守（部分更新を publish しない）。
- `active_idx` は32bitアライン変数で単一命令更新＝アトミック。ロック不要。
- マップが小さい（〜0x40B）ため memcpy コストは無視できる。

### 4.3 補足フラグ

- `STATUS.DATA_READY`：publish 後にセット、上位が全ch読了でクリア（任意）。
- `SAMPLE_COUNT`：publish 毎にインクリメント。上位が新旧を判別可能。

## 5. クロックストレッチの扱い（同期 vs 非同期）

| 方式 | 動作 | 判定 |
|------|------|------|
| **非同期キャッシュ（採用）** | 読み出しは publish 済み最新値を即返す。ストレッチ最小 | **採用**。マスタ非依存で堅牢。遅延=最大1ポーリング周期 |
| 同期オンデマンド | 読み出し時に下流フェッチを起動し、その間マスタをクロックストレッチ | 不採用（データ経路）。マスタのストレッチ非対応リスク、上流バスを数百µs〜ms占有、両バス結合 |

- データ経路は**非同期キャッシュ**とし、ストレッチは ISR がTXバイトを準備する極短時間に限定。
- 「最新の1発が欲しい」要件には、`CMD` レジスタ経由の **単発トリガ＋DATA_READYで完了通知**（§7）で対応し、データ読み出し自体はストレッチさせない。
- SMBus互換が要件なら、ストレッチ上限（25/35ms）を超えないこと。RP2040スレーブのTX準備は µsオーダで問題なし。

## 5.5 タイミング収支（要件：6ch同時・1kHzサンプル）

上位が **1ms周期で6ch分（`CH0_ANGLE`から12バイト）を読み出す** 前提で成立性を検証する。

### 5.5.1 I2C素片時間

| 速度 | 1bit | 1byte(8+ACK=9bit) |
|------|------|-------------------|
| 100 kHz (Standard) | 10 µs | 90 µs |
| 400 kHz (Fast) | 2.5 µs | 22.5 µs |
| 1 MHz (Fast+/FM+) | 1.0 µs | 9 µs |

### 5.5.2 上流：6ch一括リード（1回/ms）

`[S][ADDR+W][ptr][Sr][ADDR+R][d0..d14][NACK][P]` = 実データ 15バイト（角度12B+ミラー3B, §3.1）+ 起動/停止オーバヘッド

| 速度 | 所要時間 | 1ms予算に対する占有 |
|------|---------|--------------------|
| 100 kHz | 約 1440 µs | 144%（**不可**、1ms予算を超過） |
| 400 kHz | 約 400 µs | 40%（可） |
| 1 MHz | 約 160 µs | 16%（余裕大） |

→ **上流は 400kHz 以上必須**。100kHzは1kHz要件を満たせない。

### 5.5.3 下流：ブリッジの6chポーリング（律速）

1ch当たり = mux選択(2byte書込) + AS5600角度読出(reg設定+2byte読出) ≈ 7バイト相当

| 速度 | 1ch | **6ch巡回** | 可能ポーリングレート |
|------|-----|------------|---------------------|
| 400 kHz | 約 170 µs | **約 1020–1100 µs** | 最大 ~950 Hz |
| ~~1 MHz~~ | ~~約 70 µs~~ | ~~約 420 µs~~ | ~~最大 ~2.4 kHz~~（**TCA9548A非対応・下記⚠**）|

→ **⚠ 6ch化により下流巡回時間(~1.0-1.1ms)が上位の1msサイクルとほぼ同等〜やや上回る**。3ch時代の「全力巡回で0.55msの鮮度余裕」（§5.5.4旧版）は6chでは消失し、**平均的に1回のサンプル更新につき上位の1〜2読み出しが対応する**（オーバーサンプル/わずかな取りこぼしが常態化しうる）。上位は`SAMPLE_COUNT`/`SAMPLE_LO`で新旧判別する設計（既定機構）のため機能は破綻しないが、「毎読み出しで必ず新データ」という保証は6chでは成立しない点に注意。

> **巡回対象は有効ch（`CH_ENABLE`）のみ**：上表は6ch全有効の最悪値。1〜5ch構成（未接続chは自動的に無効, [command_spec.md](command_spec.md) §4.9/§11）では巡回が有効ch数分に短縮され、実効ポーリングレート・データ鮮度は大きく向上する（例：3ch有効なら約510-550µs巡回＝~1.8kHz相当、旧3ch設計と同等）。上位の読み出し形式（12/15バイト一括）は不変で、無効chスロットは`0xFFFF`。

> **⚠ TCA9548A は 1MHz(FM+) 非対応**：データシート（SCPS207H）Features「0 to 400kHz Clock frequency」／§7.3「supports Standard-Mode (100 kHz) and Fast-Mode (400 kHz)」より、**mux が経路にある下流バスは 400kHz が上限**。上表の 1MHz 行は TCA9548A方式では成立しない。1MHz が必要な場合は §5.6 の **PIO並列I2C方式（muxレス）** に切り替える前提でのみ有効。

### 5.5.4 データ鮮度（遅延）の設計

上位読み出しと下流ポーリングは非同期のため、最悪データ齢 ≈ 1ポーリング周期。

| 構成 | ポーリング周期 | 最悪データ齢 | 評価 |
|------|--------------|------------|------|
| **下流400kHz・6ch全力巡回（採用）** | ~1.0-1.1 ms | ~1.0-1.1 ms | **要件ギリギリ〜わずかに超過**（下記参照） |
| 下流1MHz・6ch巡回 | ~0.42 ms | ~0.42 ms | ~~予備~~（**TCA9548A非対応**。§5.6 PIO並列方式でのみ可） |

上下流は**別バス・別コア**で並行動作するため、両者は加算されず独立。律速は下流ポーリング周期。

> **【決定 2026-07-19・6ch化】上下流とも 400kHz(Fast) を維持。** ただし6ch全力巡回の周期(~1.0-1.1ms)は上位の1kHz要求とほぼ同一かわずかに長く、3ch設計時にあった0.55msの鮮度マージンは無い。実用上は`SAMPLE_COUNT`(§4.3)で新旧判別すれば機能上の問題はないが、**「全ch常に1ms以内の新鮮データ」を厳密要求する用途では6ch同時有効時に成立しない**ことを設計上の制約として明記する。鮮度を優先する場合は `CH_ENABLE` で必要ch数のみ有効化する運用を推奨（§5.5.3）。
>
> ⚠ **下流の 1MHz(FM+) 移行は不可**（TCA9548A が 400kHz 上限のため、§5.5.3 の⚠参照）。さらなる鮮度向上・オーバーサンプルが必要な場合は、mux を廃した §5.6 **PIO並列I2C方式**への移行が唯一の手段。なお**上流バス（Controller⇔RP2040、mux非経由）は将来 1MHz(FM+) 移行可能**。

### 5.5.5 ⚠ 「6ch同時」の重要な制約

**TCA9548A方式は原理的に6chを逐次（時分割）で読む**ため、ch0とch5のサンプリング時刻に**スキュー（ずれ）**が生じる。

| 下流速度 | ch0→ch5 サンプリング時刻差（スキュー） |
|---------|--------------------------------------|
| 400 kHz（TCA9548A方式・採用） | 約 850-950 µs |
| 1 MHz（§5.6 PIO並列方式のみ） | 約 350 µs |

- 各chを「独立した1kHzの点」として扱う用途（各軸を個別監視）なら、このスキューは問題になりにくい。
- **6ch間の位相・相関を厳密に比較する用途**（例：多軸の同時瞬時値でベクトル合成／位相差計測）では、このスキューが誤差要因になる。**TCA9548A方式（400kHz上限）では約850-950µs**（3ch時代の約340µsより拡大）。muxを廃した §5.6 PIO並列方式なら1MHzで約350µsまで低減可（ただし本用途では不要と判断・§5.6）。
- AS5600自体に I2C経由のハードウェア同時ラッチ機能は無いため、**mux方式では「真の同時サンプリング」は実現できない**。

真の同時性が必要な場合の代替（§5.6）。

### 5.5.6 ⚠ AS5600内部フィルタによる帯域制限

I2Cで1kHz読み出せても、AS5600の**出力段フィルタ設定（CONF: SF/FTH）**が真の応答帯域を決める。

- フィルタ後 ANGLE を使う場合、スローフィルタ 16x はステップ応答が遅く（数ms級）、1kHzで読んでも中身が更新されていない＝オーバーサンプルになる。
- 本システムは **RAW_ANGLE(0x0C/0x0D) を既定採用**（フィルタ前の生角）とし、フィルタ整定による帯域制限を受けずに1kHzの実効帯域を確保する（§11.2 / [as5600_config.md](as5600_config.md) §1）。生ノイズが問題になる場合は CONFIG で高速フィルタ側の ANGLE(0x0E/0x0F) へ切替可能。
- ⚠ SF/FTH は RAW_ANGLE には効かない可能性があり（[as5600_config.md](as5600_config.md) §3、実機検証待ち）、フィルタ効果が必要と判明した場合は ANGLE への切替で対応する。
- レジスタマップの `CONFIG`（[design_spec.md](design_spec.md) §5.2 0x30）で RAW/フィルタ角を選択可能にする方針。

## 5.6 代替案：真の同時サンプリングが必要な場合（PIO並列I2C）

「6ch同時」を厳密に満たす必要があるなら、**TCA9548Aを廃し、RP2040のPIOで独立I2Cマスタを6本立て、6個のAS5600を並列読み出し**する構成が採れる（RP2040/PIOならではの強み）。

| 項目 | TCA9548A方式（現行） | PIO並列I2C方式（代替） |
|------|---------------------|----------------------|
| 同時性 | 逐次・スキュー350〜950µs | ほぼ同時（数µs以内） |
| 部品 | mux 1個追加 | muxレス、GPIO 12本(SDA/SCL×6) |
| 実装難度 | 低（枯れたAPI） | 中（PIO I2Cマスタ実装） |
| 6ch巡回時間 | 1020〜1100µs | 1ch分（~70µs）で全ch完了 |
| 拡張性 | mux 8chまで容易 | PIO/GPIO本数に依存 |

> **【決定 2026-07-10、6ch化でも維持】要件は「各軸を個別に1kHz監視」であり位相の厳密比較は不要。よって TCA9548A方式（本命）のまま採用し、PIO並列方式は不採用。** ch間スキュー（400kHzで約850-950µs）は各軸独立監視のため許容するが、鮮度マージンが消失した点は§5.5.4のとおり設計上の制約として残る。

## 6. スレーブ実装方式（RP2040）

| 方式 | 内容 | 採否 |
|------|------|------|
| **HW I2C スレーブ** | pico-sdk `i2c_slave` API。RD_REQ / RX-FULL / STOP をIRQ処理。最大1MHz(FM+) | **採用** |
| PIO I2Cスレーブ | PIOで独自実装。特殊タイミング・回避策が必要な場合 | 予備（HWで問題時のみ） |

**ISRで扱うイベント**：
- `I2C_SLAVE_RECEIVE`：ポインタ／R/Wレジスタ書込を受領、ポインタ auto-increment。
- `I2C_SLAVE_REQUEST`（RD_REQ）：`tx_staging[ptr++]` を1バイト供給。範囲外は 0xFF。
- `I2C_SLAVE_FINISH`（STOP/RESTART）：トランザクション確定、必要ならフラグ更新。

## 7. 割込み通知線 DATA_READY / ALERT（【決定 2026-07-10：不採用】将来オプション）

> **本システムでは実装しない**（§11.3）。純1kHz周期ポーリング運用のため。以下は将来イベント駆動化が要件化した場合の参考仕様として残す。基板側は割込み用GPIOを1本予約配線しておくと後付けが容易（任意）。

上位のポーリング負荷低減・イベント駆動化のため、ブリッジ→上位への **GPIO割込み線**（オープンドレイン+プルアップ）を検討。

| 用途 | 動作 |
|------|------|
| DATA_READY | 新スナップショット publish 時にアサート。上位が読み出しでネゲート |
| ALERT/FAULT | 磁石喪失(MD=0)、AGC範囲外、下流通信エラー時にアサート |

- SMBus Alert 準拠にする場合は Alert Response Address(0x0C) 応答を実装可。
- 本線は**任意**。要件が単純周期ポーリングのみなら省略可。

## 8. エラー処理・堅牢性

| 事象 | 検出 | 対処 |
|------|------|------|
| マップ範囲外リード | ptr > map末尾 | 0xFF返却、エラーにしない（またはラップ） |
| 未定義レジスタ書込 | ptr が R領域 | 無視、`STATUS.ERR` セット |
| 下流センサ無応答（**有効ch**の故障） | 読出しNACK/タイムアウト | 該当ch旧値保持、`STATUS.chN_OK=0`、AGC=0、`DEGRADED`＋`FAULT.CHn_COMM` |
| ch未接続/未使用（**無効ch**） | 起動プローブ非応答→自動的に無効 or 上位が`CH_ENABLE`で無効化 | 巡回スキップ、角度`0xFFFF`・AGC`0xFF`・`chN_OK=0`、**DEGRADED対象外**（[command_spec.md](command_spec.md) §4.9/§11） |
| 下流バスハング | SCL/SDA固着 | Core1がバス復旧（SCL 9パルス+STOP）、必要なら TCA9548A RESET |
| 上流スレーブISR停止 | ウォッチドッグ | WDTでFWリセット（角度値は起動後再取得） |
| ポインタ暴走 | — | STOP毎に整合チェック、範囲クランプ |

> 上流バスの復旧はマスタ（上位）の責務。ブリッジはスレーブのため上流SCLを能動駆動できない点に注意。ブリッジ側はWDTで自己回復に留める。

## 9. バスパラメータ

| 項目 | 値 | 備考 |

| スレーブアドレス | 0x42（7bit, 変更可） | 予約アドレス(0x00-0x07,0x78-0x7F)回避 |

## 10. 推奨アーキテクチャまとめ

1. **通信モデル**：レジスタマップ型（ポインタ＋auto-increment）＋補助CMDレジスタ。
2. **役割**：RP2040 = HW I2Cスレーブ（0x42）。上位＝マスタ。
3. **内部**：Core0=上流応答、Core1=下流ポーリング のデュアルコア分離。
4. **整合性**：ダブルバッファ + トランザクション開始時に tx_staging へスナップショット。
5. **クロックストレッチ**：データ経路は非同期キャッシュで回避。単発取得は CMD+DATA_READY。
6. **通知**：DATA_READY/ALERT のGPIO線は任意で追加。
7. **堅牢性**：範囲外/無応答/ハングを定義済み挙動＋WDTで自己回復。

### 決定の根拠と実装への反映

#### 11.1 上位電源電圧＝3.3V系（レベル変換不要）
- 全系（Controller / RP2040 / TCA9548A / AS5600）を3.3Vで統一。RP2040は5V非トレラントのため、この統一により上流バスへのレベルシフタ（TXS0102等）挿入が不要になる。
- 上流プルアップは3.3Vへ接続（[design_spec.md](design_spec.md) §6.2）。
- ⚠ 回路設計上の担保：上位コントローラが将来5V系に変わる可能性がある場合に備え、上流SDA/SCLにレベルシフタ実装用の未実装フットプリント（0Ω/未実装で切替）を基板に残すことを推奨（コストほぼゼロの保険）。

#### 11.2 角度ソース＝RAW_ANGLE（既定）
- 既定は **RAW_ANGLE(0x0C/0x0D)** を転送する。OTP設定(ZPOS/MPOS/MANG)・0/360°境界の10LSBヒステリシスに非依存で、無設定でも予測可能な生位置が得られるため。スケーリング・オフセット・単位変換・方向正規化は上位で実施する（[as5600_config.md](as5600_config.md) §1/§4）。
- 実装：起動シーケンスで CONF=0x0A00 を揮発書込（[software_architecture.md](software_architecture.md) §8.1 手順4）。`config.angle_src` の既定値は **0（RAW）**。内部変数と CONFIGレジスタ bit0 は同一表現（0=RAW/1=ANGLE）に統一済みで `config.angle_src = CONFIG & 0x01` と素通し対応（[command_spec.md](command_spec.md) §4.4 / [software_architecture.md](software_architecture.md) §6.3）。
- CONFIG レジスタ(0x30 bit0=1) でフィルタ後 ANGLE(0x0E/0x0F) への切替を残し、フィルタ効果が必要な場合に選択できるようにする（既定は RAW_ANGLE）。
- ⚠ SF/FTH フィルタは RAW_ANGLE には効かない可能性がある（データシート p.19：RAW は "unscaled and unmodified"）。CONF の SF/FTH 選定根拠は実機検証待ち（[as5600_config.md](as5600_config.md) §3）。

#### 11.3 割込み通知線＝なし
- §7 の DATA_READY/ALERT GPIO は実装しない。上位は1kHz固定周期でポーリングする。
- データ新旧判別は `SAMPLE_COUNT`（§4.3）で、健全性・磁石検出は `STATUS`(0x02) で通知（ポーリング内で取得）。
- §7 は「将来イベント駆動化が要件化した場合のオプション」として文書に残す。基板側は割込み用GPIOを1本予約配線しておくと後付け容易（任意）。

#### 11.4 SMBus互換＝不要（生I2C）
- PEC（パケットエラーチェック）、ARA（Alert Response Address 0x0C）は非対応。
- ただしクロックストレッチはデータ経路で使わず、ISRのTX準備の極短時間（µsオーダ）に限定するため、結果的にSMBusのストレッチ上限（25/35ms）は余裕で満たす。将来SMBus要件が出ても timing 面の手戻りはない。

#### 11.5 スレーブアドレス＝0x42 確定
- 7bit 0x42。予約アドレス(0x00–0x07, 0x78–0x7F)、下流の 0x70(mux)/0x36(AS5600) と非衝突（バスも別系統）。
- 上位ドライバは Linux `i2c-dev`（`ioctl(I2C_SLAVE)` + `read/write` もしくは SMBus非依存のプレーン転送）または各MCUの標準I2Cマスタドライバを想定。ポインタ設定→リードの一般的レジスタアクセス手順（§2.2）で読める。
- ☐ 実装前アクション：上位実機での 0x42 応答と6バイト一括リードを i2c-dev 等で疎通確認（[software_architecture.md](software_architecture.md) §13「上流互換」）。アドレスは `board.h` 定数化し変更容易にしておく。

#### 11.6 将来1MHz(FM+)移行の設計マージン
- 動作速度は400kHzで確定。FM+移行余裕は **バスごとに可否が異なる** 点に注意：
  - **上流バス（Controller⇔RP2040, mux非経由）**：FM+成立可能なように設計する。RP2040スレーブTX準備はµsオーダでFM+でも問題なし（§5）。上流プルアップ値・配線長をFM+成立範囲で最適化できる余地を残す。
  - **下流バス（RP2040⇔TCA9548A⇔AS5600）**：**TCA9548A が Fast-mode(400kHz)上限・FM+非対応**（データシート SCPS207H Features / §7.3）。したがって **mux方式のままでは 1MHz 化は不可能**。下流を1MHz化する唯一の手段は、TCA9548Aを廃し §5.6 **PIO並列I2C方式** へ移行すること。
  - 下流プルアップ／配線長の最適化・AS5600短距離化は、あくまで **400kHz動作の信号品質確保** および将来のPIO並列方式移行に備えた措置として行う（TCA9548A経路の1MHz成立を目的としない）。
- ☐ 実装前アクション：下流を将来1MHz化する可能性がある場合は、TCA9548Aを前提にせず §5.6 PIO並列方式への切替を設計上の選択肢として残す（GPIO 6本分＝SDA/SCL×3 のフットプリント予約）。
